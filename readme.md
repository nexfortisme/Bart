# Bart

Bart is the next evolution of [Bot Person](https://github.com/nexfortisme/bot-person) that is built on local LLM models and the use of MCPs, Skills, and Tools. On top of being a more intuitive use of the functionality of Bot Person, it also serves as a project for me to learn more about this technology as a whole.

## What does it do?

Much like Bot Person, it takes in user input and then responds based on the responses generated by an LLM; a tool capable local model in this case, compared to the OpenAI API integration with Bot Person. The goal with Bart is to serve as basically another "person" in the chat and respond in a way that makes sense given the user input. The tools given to Bart mirror the functionality, in terms of slop generation, but also expand upon it to have greater utility.

## How it works?

Currently (still WIP), the message intent is being determined through 2 KNN classifiers, Message Intent and Tool Intent. The message intent classifier is the quick way, based on my research, to determine if a user is talking, to, about, or around the bot, and if the bot should swing into action and respond. The tool intent classifier is being used to try to speed up the responses from the LLM by giving it the limited tools it will need for the given user request, instead of tossing all of them to it and hoping for the best. This is being done in an attempt to greatly improve the speed at which message intent is being derived and also allows for quicker responses from the LLM given the user input.

  - Get the /image, and /slop command functionality tied into Bart's responses

    - ie. "Did we talk about X last week?", "When did we agree would be a good time for X?", "Did X ever mention Y?", ...
- Skills
  - Building out a little list of skills for the bot to use throughout its use.

## Feature Wishlist

- Message Queue and Load Balancing
  - I want to implement a system that allows for requests to the LLM to be automatically routed to multiple systems based on a configuration file. Since I have multiple systems that could run LLM models, at differing speeds, I want to have a system to be able to route messages across them.
- Chron Tasks
  - Have the user to be able to ask the bot to do X at Y time and have it get put into some kind of chron scheduler to do it on a recurring basis
  - Along similar lines, I would like for the bot to be able to subscribe to an RSS feed for use. Example: Steam Update Page and have it summarize patch notes
- Response Streaming
  - I alreay have something like this working on Bot Person, but I want to have Bart stream back their responses as it generates it instead of waiting for the whole response to be finished.
- API Mode
  - Have the bot run in an "API Mode" where it doesn't connect out to discord and just serves as an API endpoint for use. Thinking about it, its just abstracting an abstraction but hopefully with the MCP connections, it serves some kind of utility

## .env File Explained

| Variable | Use | Default |
| ----- | ----- | ----- |
| `DISCORD_TOKEN` | This is the secret given from the Discord Developer Portal to have the bot connect properly. Could eventually be expanded/altered to be used in other places | N/a |
| `LLM_MODEL` | The model that is going to be sent along with the requests for the main usage of the bot. Should be something that has tool capability. | `qwen/qwen3.5-9b` (mostly because it’s what can run on my hardware) |
| `EMBEDDING_MODEL` | Used in the message classification. Anything can work here as long as it’s consistent across the seed data and the usage of the bot | `text-embedding-nomic-embed-text-v1.5` (what's in LM Studio) |
| `LLM_BASE_URL` | Where the LLM model will be served from. App is built expecting it to have an OpenAI API-like structure | N/a |
| `SEARXNG_URL` | Similar to `LLM_BASE_URL`, the location of where a SearXNG instance is being hosted (used for the `web_search` tool). It should (haven't tested it) be able to also work with publicly available instances no problem, otherwise there is a self-hosting Docker container available. | N/a |
| `MCP_SERVER_ADDRESS` | Not really the address (I should rename this), but the port at which the MCP server will be hosted from within the Bart app | `:8090` |
| `MCP_URL` | This is where the MCP client from within the bot will connect to. Since it’s inside the same application, the default should apply for normal use | `http://localhost:8090/mcp` |
| `FETCHER_MCP_ENDPOINT` | The location of the fetcher MCP HTTP endpoint used by the web fetch tools. Bart will fall back to `PLAYWRIGHT_MCP_ENDPOINT` for backward compatibility, but `FETCHER_MCP_ENDPOINT` is the preferred variable now. | `http://localhost:3000/mcp` |

## Running the Application

You'll need:

- Golang
  - Probably the most up-to-date version
- Model Hosting with OpenAI API-Like structure
  - I use LM Studio but Ollama probably would work just as well
- SearXNG Instance
  - I'm running it through a Docker Container and it seems simple enough. Find docs on the [SearXNG Website](https://docs.searxng.org/admin/installation-docker.html)
- Fetcher MCP
  - Bart now expects a fetcher MCP-compatible server that exposes `fetch_url` and `fetch_urls`. I still recommend running it locally over HTTP and pointing `FETCHER_MCP_ENDPOINT` at it. I'm running it via docker, find the docs on the [GitHub Page](https://github.com/jae-jae/fetcher-mcp?tab=readme-ov-file#deploying-with-docker-compose)

It feels like a lot and I'm reasonably confident that there is a better way to handle all of this, but I'm just one dude, so cut me some slack.
